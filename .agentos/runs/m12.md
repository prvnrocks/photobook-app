### What the code does today
- **Supabase clients** (`src/lib/supabase/{admin,server,middleware,client}.ts`): none of them sets a custom `fetch` or a timeout. Storage-js has no timeout option at all.
- **Built-in retries** (postgrest-js 2.118): it already retries GET/HEAD up to 3 times on 520/503 or network errors, with 1, 2 and 4 s delays. A fetch error always comes back with `code: ""`.
- **Error codes**: there are 126 sites in `src/lib/db/*` that build `XQueryError(op, error.code)`, so the timeout signal has to reach them through `error.code`.
- **`getCurrentUser()`** returns `null` on any auth error. So a hung or failed Auth call becomes a **401 or a login redirect**, not a "try again".
- **Client side**: `drive.ts` has a 90 s deadline per advance request and treats 5xx as transient. **`finalize-client.ts` has no deadline**: a hung finalize stalls the upload screen. Autosave retries 429/5xx.
- **Real bug (timeout after the write landed):** `saveDocIfRev` (`src/lib/db/books.ts:391`) does an UPDATE only if `doc_rev = baseRev`. If that UPDATE commits but the response is lost, the retry finds 0 rows and answers "conflict". The user then sees "Changed in another tab – Reload" when nothing else changed.
- **AI lease budget**: `LEASE_MARGIN_MS` is 20 s, but a checkpoint write (10 s) plus the release RPC (15 s) under the new budgets can take 25 s.

### Fetch deadline design (one approach)
New file `src/lib/supabase/deadline.ts`. It must not import `server-only`, so the browser client can use it too. `createDeadlineFetch(profile: "server" | "browser")` is passed as `global.fetch` to `createClient` (admin), `createServerClient` (server and middleware) and `createBrowserClient`. It sorts each request by URL and method:

| Class | Match | Server | Browser |
|---|---|---|---|
| auth | `/auth/v1/*` | 8 s (middleware 5 s) | 20 s |
| rest | `/rest/v1/*` except rpc | 10 s, **one retry for GET/HEAD only** | 20 s, one retry for GET/HEAD |
| rpc | `/rest/v1/rpc/*` | 15 s; 60 s for `cleanup_*`, `delete_book_guarded`, `reap_stale_agent_runs`, `admin_ai_spend_daily` | 20 s |
| storage-json | sign / list / remove / info, i.e. `createSignedUrl(s)` | 15 s | 20 s |
| storage-upload | POST/PUT `/storage/v1/object/{bucket}/…` | 30 s + bytes at 1 MB/s, max 120 s (a 50 MB PDF gets 80 s) | 30 s + bytes at 16 KB/s, max 600 s |
| storage-download | GET object | 60 s, or the caller's signal (`images.ts` keeps its own 30 s) | 60 s |

Rules:
- **On timeout, return a fake response instead of throwing.** The wrapper answers `504` with body `{code:"SUPABASE_TIMEOUT", statusCode:"SUPABASE_TIMEOUT", error:"timeout", message}`. Each library then handles it on its normal path:
  - postgrest puts `SUPABASE_TIMEOUT` in `error.code`, so all 126 existing sites carry it with no edits, and it does not retry a 504.
  - storage-js returns `StorageApiError.statusCode`, which `storageCode()` already reads.
  - auth-js returns `AuthRetryableFetchError`.
- **Caller cancels still win.** If the caller's own signal (`.abortSignal()`, PDF job) fires, the original AbortError is rethrown, not turned into a timeout.
- **The deadline covers the whole response.** For auth, rest, rpc and storage-json the wrapper reads the body inside the deadline and returns a rebuilt Response. For downloads it passes the signal so a stalled body also aborts.
- **Request bodies are never read or cloned.** Size is measured only for Blob, ArrayBuffer, typed arrays and strings. A stream or unknown body gets the maximum upload budget, so streaming uploads keep working.
- **No `AbortSignal.any` or `AbortSignal.timeout`.** It uses a manual AbortController plus setTimeout, because iOS 16 Safari and the Edge middleware runtime can't be relied on to have them. `globalThis.fetch` is read at call time so tests can stub it.
- **Helpers:** `isSupabaseTimeout(err)` (checks for the `SUPABASE_TIMEOUT` code or statusCode), and `SupabaseUnavailableError` (code `SUPABASE_TIMEOUT`) for auth.

What each layer does on a timeout:
- `getCurrentUser()` throws `SupabaseUnavailableError` on `AuthRetryableFetchError`. It keeps returning `null` for real auth errors.
- A new helper in `src/lib/http/json.ts`, `unavailableIfTimeout(err)`, returns `503 {error:"unavailable"}` with `Retry-After: 3`. It is used in every API route's catch block.
- Middleware: if `getUser` times out on a protected path, it returns a 503 "temporarily unavailable" page instead of redirecting to login. Public paths carry on as now.
- Server components throw and the M11 `error.tsx` shows "Try again". Server actions return their existing generic error result.

**Everything affected:**
- API routes: `ai/rewrite`, `ai/runs` (POST), `ai/runs/[id]` (GET), `ai/runs/[id]/advance`, `books/[id]/doc`, `books/[id]/finalize`, `books/[id]/pdf` (plus the render in `after()`), `books/[id]/pdf/status`, `books/[id]/photo-urls`, `cron/cleanup`, `email/unsubscribe`, `stripe/webhook`, `b/[slug]/og`, `auth/callback`, `auth/confirm`.
- Server actions: `auth`, `b/[slug]` (unlock), `books`, `books/[id]/{edit,publish,review,upgrade}`, `settings`.
- Middleware, and the 31 files that call `getCurrentUser`.
- Browser: the upload queue (`supabase-adapters.ts`) and auth refresh.

**Retries and idempotency when a timeout hides a write that landed:**
- **Autosave**: on 0 rows, read `doc_rev` and `doc`. If `doc_rev === baseRev + 1` and a key-sorted canonical JSON of the stored doc equals the sent doc, return ok with that rev. This is task T3.
- **Finalize**: every step is safe to repeat (duplicate groups recomputed, places and colours only fill nulls; the builder must confirm the fallback album also only writes when absent). Return 503 with `Retry-After: 10` to match the one-run-per-10-s limit. The client treats 503 like 429 and gets a 75 s deadline (the route's limit is 60 s).
- **AI tick / advance**: a timed-out checkpoint throws, the `finally` releases the lease (with its own budget), and the route returns 503. `drive.ts` backs off. If the release also failed, retries get 202 until the lease ends (240 s or less). Raise `LEASE_MARGIN_MS` to 30 s and add a test that Storyteller time plus margin fits in the lease, and that the margin covers write plus release. A start-run retry gets `already_running`; confirm the route resumes the active run.
- **Rewrite**: a timeout after the capped insert uses up one rewrite. Accepted and documented.
- **PDF export lease**: if the upload timed out after it actually stored the file, the next attempt hits 409 and the existing remove-and-retry handles it. `claim_export` lease = `maxDuration`, so a dead job frees itself. Risk: an upload that starts late can run past the 270 s job deadline. The deadline race still answers, and the 300 s lease covers it.
- **Stripe webhook**: timeout returns 503 and Stripe retries. `fulfill_book_checkout` dedupes on event id, so a replay of a committed event returns `duplicate`, which gives 200.
- **Cron**: a sweep that times out is counted as failed and the next sweep runs. Confirm `sweep()` catches it.
- **Browser upload**: the 504 has `status` ≥ 500, so the queue's `isRetryable` already retries it. Uploads use `upsert: true`, and photo-row inserts already reconcile by fingerprint.

### Risks
- **Slow phone networks**: a legitimate upload on a very slow connection could hit the size-based limit and retry from scratch. The rate used (16 KB/s, up to 600 s) is deliberately generous. Real stall detection would need XHR progress events, which is out of scope.
- **Writes keep running after we give up**: aborting on our side does not cancel the query in Postgres. A timed-out write can still commit, which is why T3 exists.
- **getCurrentUser behaviour change**: it now throws on timeout, so T2 must check all 31 callers. Any page that redirects on `null` must not catch and swallow the new error.
- **Lease timing**: the 20 s to 30 s margin change shortens how long the Storyteller is allowed to start before a lease ends. 180 + 30 = 210 s, still within 240.
- **PDF upload near the 270 s deadline**: an upload that starts late can run past it (covered by the 300 s lease).

### Decision for the user
**D1, emoji in PDF captions.**
- (a) Defer to after launch. This is my recommendation, to keep M12 small.
- (b) Pull it in. That means bundling a static monochrome Noto Emoji font for print. Variable fonts end up as Type3 in the PDF (a lesson from M8), so it has to be a static instance. It also bumps `PDF_RENDERER_VERSION`, so each paid book's next PDF re-renders once and counts toward the daily limit.
